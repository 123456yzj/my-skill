# 规则转换

仅整理已有纠错文件，将其中的规则提炼、合并到目标项目实际使用的规范。输入依据是文件内容。

## 共用路径与写入边界

- 目标项目根目录取自当前会话的目标工作区；从子目录工作时结合工作区信息、版本库根目录及规范入口确认。多项目且目标不明确时，只确认目标项目，不要求用户输入纠错文件路径。
- 输入固定为项目根目录下的 `.agents/corrections/rules.md`。记录目录固定为同一根目录下的 `.agents/corrections/records/`。所有数据路径相对于目标项目根目录，不相对于 skill 安装目录或当前子目录。
- 用户决定前不写入任何文件，包括规范、纠错文件、计划、临时文件、日志、备份、占位文件或记录。提案与检查只在对话中完成；只使用不会产生文件的检索、读取与检查方式。
- 启动转换不等于同意具体方案。同意必须对应展示的整合文本、位置和操作；已获准的同一方案无需重复确认。拒绝、暂缓或尚未回答时保留对话提案；修改后的实质方案再次交由用户决定。
- 现有机制若要求提前写计划或自动记录，在对话中提出冲突及修改建议，不自动运行旧写入流程或修改现有机制。无法解决的约束先说明并等待用户决定。

## 1. 只读取已有输入

读取 `.agents/corrections/rules.md` 的每条 `SCN`、`RSN`、`CNT`、`TIME`，保持来源场景和限定条件。`TIME` 只表示纠正时间，不能据此判定较新规则自动覆盖已有规范。

- 文件不存在或没有规则：说明无可整理输入并结束，不初始化纠错文件，不生成记录。
- 格式有歧义、字段缺失或规则相互矛盾：在对话中列出问题和整理建议，不猜测缺失语义或擅自修复文件。
- 用户同时提出新规则：说明本次整理范围是文件内已有内容，不把对话要求当作源规则补入。

## 2. 提炼与合并

以“触发场景 → 应采取的行为 → 原因”理解每条规则，先按问题和职责分组，再决定合并方式。原规则是范围依据，不能从单个案例推导全项目无条件要求。

| 对照结果 | 处理方法 |
| --- | --- |
| 已有规范完整覆盖 | 标记为已覆盖，不重复添加；说明实际覆盖位置 |
| 同场景、同方向的多条规则 | 合并共同原则，保留影响决策的限制和差异 |
| 场景不同且行为不同 | 分开或写明确条件分支，不抹去场景差异 |
| 局部案例可形成原则 | 只在原场景支持的范围内提炼；不添加无依据义务 |
| 现有条目含糊或不完整 | 优先改善原条目，展示替换前后的完整含义 |
| 同场景要求相反 | 展示双方依据和协调选项，由用户决定；不按时间或措辞强弱自动覆盖 |

规则表达应说明在什么条件下做出什么选择，去除偶然的实现细节。避免具体编码步骤，也避免“保持代码整洁”这类无法执行的表述。提炼后反向核对每条来源：适用边界有无扩大，限制有无丢失，有无新添要求。

## 3. 根据现有规范确定落点

从目标项目实际 agent 入口、规范引用和任务路由读取相关规范、示例及 skill，核对重复和冲突。不要预设规范放在某个业务文件或目录。

按职责选择最窄且充分的落点：局部要求进入对应局部规范，工作流要求进入相关流程，共同原则才考虑通用入口。优先更新已有条目，避免把相同规则复制到多处。

为每项候选确认后续 agent 如何命中该场景并读取规则：已有入口会直接加载、通过有效引用读取，还是需要补充路由。新增规范或入口链接也必须纳入提案，不把“文件已存在”视为可被加载的证据。没有合适位置时，根据项目结构提出新位置和加载入口，未经用户同意不创建。

检查实际读取的规范、示例和相关 skill 是否一致；发现冲突展示位置和协调文本。说明读取范围和未验证之处，不宣称检查了未读取内容。

## 4. 在对话中提交可落实的方案

逐项展示：

1. 来源规则主题及归并关系、已覆盖或保留待处理的条目。
2. 提炼后的完整规范文本，以及提炼、合并或跳过的理由。
3. 拟新增或修改的目标项目相对路径、标题或条目；修改时展示原文与替换文本。
4. 覆盖、重复、冲突检查结果；如需协调示例、skill 或入口，列出具体改动文本。
5. 后续加载入口和有效引用路径，以及本次整合记录的内容预览。
6. 源文件处理方式：默认保留。仅在用户同意的方案明确包含删除操作时，移除已确认完整覆盖或已成功整合的条目；部分整合、冲突未解决的条目必须保留。

请求用户同意具体方案后再落实。部分同意只执行获准部分，未获准内容不写入。源文件保留时，每次重新对照现有规范判断已覆盖项，不重复转换；不添加状态字段、不另建处理索引、不自动归档或清空。

## 5. 同意后落实与验证

1. 重新读取源文件、获准目标及其引用入口。若出现影响方案的变更，回到对话更新提案；不覆盖并发修改。
2. 按批准范围更新规范及必要入口，回读确认提炼文本、场景、引用路径和相关内容一致。只检查获准方案所需内容；不顺便改业务代码。
3. 若已批准删除源条目，只在对应规范已成功写入并验证后删除。保留其他条目，源文件仍遵循 `SCN`、`RSN`、`CNT`、`TIME` 顺序和 `YYYY-MM-DD HH:mm:ss` 时间格式。
4. 整合完成后按需创建 `.agents/corrections/records/`，每次生成独立文件，以本地实际生成时间按 `YYYYMMDD-HHmmss.md` 命名。若同秒文件已存在，等到下一可用实际秒重新取时并确认不存在；不覆盖、不添加不符合格式的后缀。
5. 记录仅包含整合内容和整合位置，内容须对应已经完成并验证的获准整合，位置写目标项目相对路径及标题或条目。不得加入来源、审批、理由、过程、历史或状态信息。
6. 回读记录核对命名、两个内容区和实际落点，在对话中报告规范、入口、源文件处理及记录位置。

记录模板：

```markdown
# 整合记录

## 整合内容

- 本次形成或调整后的完整规则。

## 整合位置

- 目标项目相对路径：对应标题或条目。
```

所有规则均已覆盖且未实施规范整合时，只在对话报告结果，不产生空记录。写入或验证中途失败时停止后续删除，不将未完成项写成已完成；在对话报告实际改动和剩余问题。规范已完成但记录写入失败时如实报告记录缺失，在授权范围内补写，不声称整个流程已完成。
