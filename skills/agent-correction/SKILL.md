# 纠错

理解用户纠正的场景，将可重复适用的要求整理成规则，在对话中检查和提交，用户同意后保存。不要把一次任务的正确结果直接扩大为全局要求。

## 共用路径与写入边界

- 目标项目根目录取自当前会话的目标工作区；从子目录工作时结合工作区信息、版本库根目录及规范入口确认。多项目且目标不明确时，只确认目标项目，不要求用户输入纠错文件路径。
- 纠错文件固定为项目根目录下的 `.agents/corrections/rules.md`。路径相对于目标项目根目录，不相对于 skill 安装目录或当前子目录。
- 用户决定前不写入任何文件，包括纠错文件、目录占位文件、计划、临时文件、日志、备份和整合记录。提案和检查结果仅留在对话中；只使用不会产生文件的检索、读取与检查方式。
- 调用 skill、纠正一次行为或要求“记住”表示启动提案流程，不能代替用户对具体规则的同意。同意必须对应已展示的规则和写入操作；已获准的同一提案无需重复确认。
- 如现有机制要求提前写计划或自动记录事件，在对话中指出冲突并建议调整入口；不自动执行旧写入流程，不自行修改现有机制。无法解决的约束先说明并等待用户决定。

## 1. 理解场景

从原需求、用户纠正、已知任务结果中判断：纠正了什么决策，为什么需要纠正，何时应采用纠正后的做法。缺少决定适用范围的信息时在对话中澄清，不推测业务规则。

区分三种情况：

- 一次性任务要求：当前任务遵守即可，说明不建议保存为持续规则。
- 已有规范的执行偏差：指出对应规范，优先建议遵守或澄清原条目，不制造同义规则。
- 可重复的场景要求：形成候选规则，保留用户给出的范围、前提与限制。

## 2. 检查覆盖、重复与冲突

读取已有纠错文件（不存在视为无已保存规则，不创建文件），从目标项目实际规范入口定位相关内容。入口可能是 agent 指令、规范目录、工作流或相关 skill；沿已存在的引用读取，不假定业务规范的文件名或位置。

逐项比对触发场景、行为要求和原因，而非只比对文字：

- 完整覆盖：展示对应位置，建议不新增。
- 同场景同方向但表达不清：提出澄清或替换已有纠错条目的方案。
- 不同场景要求不同：保留各自条件，不合并成无条件规则。
- 同场景要求相反：展示冲突文本、位置与协调建议，用户决定前不选择覆盖。

只报告实际读取范围的结论；不可读取的规范说明为未检查，不宣称全项目无冲突。提案中的写入范围为纠错文件。

## 3. 在对话中提交提案

说明判断、已检查的规范位置、重复或冲突结论、拟新增或替换的条目及写入位置。替换时展示原条目和新条目。每条按如下格式展示：

```markdown
## 简短的规则主题

- SCN：明确触发场景，必要的适用限制直接写在这里。
- RSN：说明纠正原因及需要避免的问题。
- CNT：表达在该场景下应该怎么做，方向明确且足以指导行动。
- TIME：YYYY-MM-DD HH:mm:ss
```

`TIME` 在提案中可以暂用上述格式占位，明确同意后保存时填入本地实际时间。其余内容须完整展示，不以占位文本请求批准。

`CNT` 使用规范性、正向表述，避免绑定某次实现的函数名、组件名、代码片段、具体文件名或操作步骤。必要条件写在 `SCN`，不单列例外、检查要点或历史字段。不要把规则提炼成“保持质量”等无法指导决策的口号。

明确请求用户决定是否按展示内容写入。拒绝、暂缓或尚未回答时，结束在对话提案；用户修改要求时更新提案，待用户同意最终版本。部分同意时只处理获准条目。

## 4. 同意后保存与核对

1. 重新读取纠错文件及相关规范，确认提案依据未改变。若出现影响规则意义的变更，回到对话更新提案；不扩大批准范围。
2. 仅此时按需创建 `.agents/corrections/` 和 `rules.md`。文件用 Markdown，首行可为 `# 纠正规则`；每条用二级主题标题和四个非空字段，依次为 `SCN`、`RSN`、`CNT`、`TIME`，时间必须是实际有效的 `YYYY-MM-DD HH:mm:ss`。
3. 新增只追加获准条目；替换只更新用户同意的条目，更新时间。保留其他内容，不保存原始对话、审批过程、事件历史或旧版本。
4. 如果原文件格式不符，先在对话提出整理方案，未经批准不重写原文件。
5. 回读确认字段顺序、时间、文本和改动范围，报告保存位置与内容。写入失败如实说明已完成与未完成部分，不声称已保存。
