# 需求交付与界面验收依据

目标是让前端明确要实现的行为，让测试能够判断结果。需求就绪、实现完成和测试通过是不同结论，分别说明范围与依据。

## 需求交付检查

| 方面 | 就绪要求 |
| :--- | :--- |
| 目标与范围 | 用户任务、页面或区域、影响对象及期望变化明确 |
| 业务与契约 | 权限、状态、校验、枚举、接口行为有实际依据，未决项明确 |
| 功能与交互 | 位置、初始、触发和结果可执行，联动条件和操作后果完整 |
| 状态与恢复 | 适用的加载、空数据、失败、成功、输入保留和返回行为明确 |
| 界面与适配 | 必要信息、入口、视觉语义、相关设备与输入方式可检查 |
| 验收任务 | 每个功能有对应场景，前置条件、数据、步骤和预期可判断 |

普通字段或局部需求按适用内容裁剪，复杂需求再补结构与方案取舍。不要求固定指标数、布局、多方案、主题或分数。

需求结论使用明确描述：

- **可交付**：相关条目已明确，实施和验收不需猜关键行为。
- **需补充**：存在可定位遗漏或冲突，说明修改位置。
- **待确认**：关键业务、接口或交互选择缺失，说明受影响条目；独立明确部分可先交付。

业务能力、权限、提交边界和接口语义不能由视觉偏好覆盖。文档存在不等于全部条目已确认；提出的建议保留其确认状态。

## 验收场景编写

按功能与风险确定覆盖：正常操作、权限、校验、回填与重置、联动、失败恢复、连续操作及相关视口/主题。预期结果应描述可观察行为，避免“体验良好”“更高级”等无法判断的要求。

记录测试所需账号、数据、接口环境和故障条件。尚未执行的场景为验收任务，不能预填通过或虚构证据。

## 实现结果复核

| 结果 | 依据 |
| :--- | :--- |
| 满足 | 有实际证据支持对应验收条件，并明确检查范围 |
| 有偏差 | 实际行为与确认要求不同，提供功能/验收编号和证据 |
| 未验证 | 缺少环境、数据或运行证据，说明所需条件 |

需求说明是预期依据；实现、工程检查与执行记录由实施和测试方提供。源码能说明实现意图，不能替代运行行为证据。未经用户测试不宣称效率提升或给出改善比例。

不要根据像不像某产品、卡片数量、边框或颜色形式判定质量；应说明对任务的影响。复核当前授权范围，不以复核结果代替发布决定。
