# DESIGN DNA: 任务清晰与业务可辨

> 企业后台的设计方向是克制、清晰、内容优先。用户任务、业务契约与宿主设计系统优先于任何视觉偏好。

## 设计决策的共同依据

每项布局、颜色或交互选择都应说明：服务的任务、适用场景、带来的收益、付出的代价，以及如何验证。不要仅以“更极简”或“更高级”解释设计。

| 决策 | 适用与收益 | 代价与例外 | 验证 |
| :--- | :--- | :--- | :--- |
| 边界与容器 | 独立实体、编辑范围、状态归属需要辨认时保留边框或弱背景；重复外壳可简化 | 去掉边界可能令规则和操作归属混淆；增加边界可能降低信息密度 | 用户能否指出当前对象和操作作用范围 |
| 留白与密度 | 用分组间距组织阅读；按视口、连续工作时长和数据规模选择标准或紧凑密度 | 间距过大增加滚动，过小增加串行误读 | 真实数据下定位、扫描、比对是否顺畅 |
| 色彩 | 沿用宿主品牌与语义色；用状态色突出异常、成功或数据类别，并辅以文字/图形 | 多色争夺注意力；单色可能混淆选中态与异常态 | 用户能否区分状态、当前选择和可操作入口 |
| 默认可见性 | 依频率、决策必要性、比较需求及遗漏风险决定 | 隐藏降低视觉负担，却可能增加展开、切换和记忆成本 | 完成任务时是否漏看必要依据、反复切换 |
| 编辑载体 | 行内、抽屉、独立页面或并列面板按任务时长、宽度和上下文选用 | 抽屉可能遮挡比较对象；独立页面可能失去列表上下文 | 编辑空间、返回路径及上下文是否足够 |

## 业务优先于审美

- 展示层可以汇总和对比，但不能合并独立的实体、策略、生效期、权限或提交边界。
- 完成当前决策必需的信息，即便低频也不能仅为视觉降噪而隐藏。
- 不显示技术字段不代表从业务状态、请求或审计中删除；需要排错的 ID 保留可复制入口。
- 指标计算须先核实口径、单位、时间范围、缺失值和零基数，不为了填充页面制造 Delta。

## 执行顺序

整体需求设计按“任务与契约 -> 信息及比较关系 -> 交互和状态 -> 必要视觉要求 -> 需求说明与验收场景 -> 交付检查”推进；局部任务只处理受影响部分。三类典型任务的状态与选择条件见 `COMPONENT_RULES.md`，视觉参考见 `DESIGN_TOKENS.md`，交付与验收依据见 `UI_QUALITY_STANDARD.md`。
