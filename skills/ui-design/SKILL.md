# UI 与功能需求设计

将用户意图、已有业务规则和数据契约整理成一份当前需求说明，为前端实施和验收测试提供共同依据。按任务需要完成产品分析、信息组织、交互和视觉设计。

## 职责与依据

- 写清在哪个页面或区域增加什么功能、何时触发、影响哪些对象、各状态如何表现，以及怎样验收。布局、线框和视觉方案服务于这些要求。
- 可读取现有代码、类型、接口和运行页面以核实行为。文件目录、组件拆分、状态管理实现、样式技术和测试代码由实施方依据项目规范决定。
- 从目标项目实际入口检索业务规范、设计系统与已有界面能力，沿有效引用按需读取。不要推测规范位置或共享组件名称。
- 用户明确要求和项目已确认的业务、权限及接口契约是约束；内部设计资料是决策方法和参考。示例中的布局、数量、尺寸和配色不作为默认答案。
- 字段存在不代表必须展示、允许编辑或可用于筛选；接口存在不代表所有用户或状态均可调用。关键业务含义或交互选择缺失时先检索，再定向澄清。

## 1. 理解并分流

明确目标、页面与区域、当前行为、期望变化、数据依据和任务范围。区分已确认事实、现状观察、设计建议及待确认项。

| 主要目标 | 工作流 |
| :--- | :--- |
| 字段添加、字段联动、明确局部功能或视觉问题 | [局部改善](workflows/ui-improvement.md) |
| 指标、趋势、告警、刷新和下钻任务 | [看板设计](workflows/dashboard-design.md) |
| 理解 API / DTO / JSON 的业务含义并组织展示与操作 | [数据转译](workflows/data-driven-ui.md) |
| 从需求形成新页面或模块的功能与任务结构 | [新产品设计](workflows/new-product-design.md) |
| 整体重组现有界面的信息或操作路径 | [界面重组](workflows/ui-redesign.md) |

按主要目标选择一条工作流。局部任务不因页面包含看板或复杂数据升级为整体设计；截图或 DTO 只是输入材料。“太乱”“不好看”等模糊描述先检查现状。

只读取当前任务所需方法，不加载全部资料，不要求建立专家团。以下文档均是本 skill 的内部方法：

| 信息组织与可见性 | [information-architecture](methods/information-architecture.md) |
| 操作路径与布局选择 | [ux-architecture](methods/ux-architecture.md) |
| 字段语义与数据表达 | [data-ui-designer](methods/data-ui-designer.md) |
| 设计规范复用与补充 | [design-system-builder](methods/design-system-builder.md) |
| 视觉与界面状态 | [visual-system-designer](methods/visual-system-designer.md) |

普通字段或局部功能无需完整信息分类、多方案比较或视觉稿。涉及整体结构的任务再补相应设计。主题、设备与可访问性要求按目标项目和使用场景确定。

## 3. 形成共同交付

以 [需求说明模板](templates/requirements.template.md) 组织当前需求，按用户任务划分稳定的 `REQ-01` 等功能编号，以 `AC-01` 等验收编号关联功能。

- 前端读取整体目标、自己负责的功能、数据契约和依赖；测试读取对应验收场景。紧密关联的字段行为归为同一功能，避免按字段机械拆分。
- 每项功能说明位置、初始状态、触发条件、行为结果、接口映射、权限与校验、异常恢复及受影响适配；无关内容省略，不补造业务能力。
- 每项验收说明前置条件和数据、操作步骤、预期结果与关联功能。未执行的场景是测试任务，不填“通过”。
- 不同方法的结论汇入同一说明。其他模板仅是可选段落骨架，按需纳入正文或已存在的附件，不强制产生多份分析报告。
- 关键未决事项标明影响与所需确认，可独立实施的条目和受阻条目分开说明。建议经用户或对应负责人确认后才成为确定要求。

## 4. 保存与交接

需要持久交付时优先更新目标项目已存在的当前需求文档，沿用其位置、结构和版本约定。没有现有约定时，在对话中提出项目相对落点。仅讨论或用户要求先看方案时在对话中交付；获准保存后再写文件。明确要求输出需求文档时可直接按约定保存，不重复确认。

只更新本次需求相关内容。变更保留已有功能编号，说明受影响的功能、验收编号和依赖，并向实施与测试方交接最新版本。任务委派按用户要求进行，不自动启动子代理。

## 5. 交付检查与结果复核

按 [质量标准](design-system/UI_QUALITY_STANDARD.md) 检查前端是否还需猜测关键行为、测试是否能明确判断结果、条目是否与实际契约一致。需求说明可就绪，不代表代码已经完成或测试通过。

用户提供实现结果并要求复核时，再逐项比对验收场景与证据，报告满足、偏差和未验证项。实际测试执行、工程检查与缺陷修复交给对应实施或测试任务。
